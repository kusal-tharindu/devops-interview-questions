# Redis Architecture & Ecosystem Guide

## 1. Overview: What is Modern Redis?

Redis is an in-memory, key-value data structure store engineered for sub-millisecond response times. While historically known as a high-performance **cache**, modern Redis functions as a multi-model primary database, message broker, and streaming engine.

### Core Capabilities Beyond Caching
- **Rich Data Structures**: Strings, Hashes, Lists, Sets, Sorted Sets ($ZSET$), Bitmaps, HyperLogLogs, Geospatial indexes, and Streams.
- **Document & Query Engine (formerly RedisJSON / RediSearch)**: Native JSON document storage with secondary indexing, full-text search, and aggregation.
- **Vector Search Engine**: High-performance approximate nearest neighbor ($ANN$) search (HNSW and FLAT indexing) for AI embeddings and LLM semantic caching.
- **Time Series & Probabilistic Structures**: Dedicated time series downsampling, Bloom filters, Cuckoo filters, Count-Min sketches, and Top-K.

> [!NOTE] Industry Context: Licensing & Valkey (Interview Essential)
> In March 2024, Redis transitioned future releases from the open-source BSD 3-Clause license to dual source-available licensing (**RSALv2** and **SSPLv1**). 
> - **The Implication**: Cloud providers cannot offer Redis as a managed service without a commercial agreement with Redis Ltd.
> - **Open Source Fork**: The Linux Foundation and major tech companies (AWS, Google, Oracle, Ericsson) subsequently launched **Valkey**, an open-source BSD fork continuing from Redis 7.2.

## 3. High Availability & Architecture: Community vs. Enterprise

Interviewers frequently probe the difference between how open-source Redis achieves HA versus how Enterprise implementations work.

### Community HA: Sentinel vs. OSS Cluster
- **Redis Sentinel**:
  - Used for non-clustered, single-master topologies.
  - Separate Sentinel processes monitor the master, initiate consensus-based election on failure, and reconfigure replicas.
  - *Limitation*: Write scalability is capped at a single master node.
- **OSS Cluster Mode**:
  - Splits data across 16,384 fixed **hash slots** (`HASH_SLOT = CRC16(key) mod 16384`).
  - Uses a peer-to-peer gossip protocol between nodes.
  - *Client Burden*: The client application **must** be cluster-aware. If a requested key resides on a different node, the node returns a `-MOVED` or `-ASK` error, forcing the client to re-route the query.

### Enterprise Architecture: The Proxy Pattern
Redis Software and Redis Cloud resolve client complexity by decoupling the **Control Plane** from the **Data Path**:

```
                         ┌────────────────────────────────────────────────────────┐
                         │                  Redis Software Cluster                │
                         │                                                        │
                         │   ┌────────────────────────────────────────────────┐   │
                         │   │       Cluster Management Plane (BDB, Mgmt)     │   │
                         │   │       • Health checks   • Auto-failover        │   │
                         │   │       • Resource placement                     │   │
                         │   └───────────────────────┬────────────────────────┘   │
                         │                           │ controls                   │
                         │                           ▼                            │
Standard Client ────────►│ ───► [ DMC Zero-Latency Proxy ]                        │
(No cluster library req) │                    │                                   │
                         │         routes to shards transparently                 │
                         │                    ▼                                   │
                         │      [Shard 1]   [Shard 2]   [Shard 3] (Engine RAM)    │
                         └────────────────────────────────────────────────────────┘
```

1. **Management Path**: Handles cluster quorum, health checks, automated node failover, licensing, and metric collection.
2. **Data Path (DMC - Dynamic Multi-Core Proxy)**: 
   - A high-performance proxy intercepts inbound client connections.
   - Any standard (non-cluster) Redis driver can connect to a single endpoint.
   - The proxy transparently distributes and routes commands to the correct underlying shard.
3. **Active-Active (CRDTs)**:
   - Uses Conflict-Free Replicated Data Types to allow concurrent, local-latency writes in multiple geographic regions with guaranteed eventual consistency and automated conflict resolution.

## 4. Redis Software Deployment Planning (VM Prerequisites)

When self-hosting Redis Software on Virtual Machines, production readiness requires specific infrastructure, network, and DNS configurations.

### 1. Quorum & Node Sizing
- **Node Count**: Minimum **3 nodes** (virtual machines) spread across failure domains to form a consensus quorum and prevent split-brain scenarios.
- **OS Support**: Enterprise Linux (Red Hat Enterprise Linux, Ubuntu Server, Rocky Linux).
- **Memory ($RAM$)**: Sized for the working set + replication buffers + headroom for copy-on-write during snapshotting.
- **Storage**: Persistent SSD/NVMe attached to each VM for:
  - Append-Only File ($AOF$) logs
  - Snapshot files ($RDB$)
  - Cluster configuration state and audit logs

### 2. Network Topology & Ports
- All VM nodes must reside on a dedicated, low-latency private subnet / VPC.
- Internal communication between nodes must be unrestricted across cluster gossip and management ports.
- Client access must be restricted via security groups to designated application tiers or API gateways.

### 3. Cluster DNS Configuration
Redis Software manages endpoints dynamically using an authoritative DNS delegation model:

```
External DNS Provider                          Redis Software VMs
┌──────────────────────┐                     ┌────────────────────────┐
│ A Record (node1.net) ├────────────────────►│ VM 1 (e.g., 10.0.1.11) │
│ A Record (node2.net) ├────────────────────►│ VM 2 (e.g., 10.0.1.12) │
│ A Record (node3.net) ├────────────────────►│ VM 3 (e.g., 10.0.1.13) │
│                      │                     └────────────────────────┘
│ NS Record            │                                  ▲
│ (cluster.domain.com) ├──────────────────────────────────┘
│ delegates to A-recs  │ (Nodes act as authoritative Name Servers for all
└──────────────────────┘  database endpoints: *.cluster.domain.com)
```

- **Glue Records (`A` Records)**: Created in corporate DNS, mapping each node's fully qualified domain name directly to its static IP.
- **Delegation Records (`NS` Records)**: Point the root cluster subdomain to the VM `A` records.
- **Why this matters**: As databases and shards are created, moved, or failed over, the internal Redis DNS services instantly resolve the database endpoint to the active proxy without manual DNS administration.

```
         ┌─────────┴─────────┐                               │
         ▼                   ▼                         ┌─────┴─────┐
        No                  Yes                        ▼           ▼
  [Redis Cloud]     [Redis Community]          [Redis Software]   [Redis Community]
  (Zero ops,         (If budget is $0,         (Enterprise SLAs,   (Low budget,
   managed DBaaS)     DIY ops acceptable)       CRDTs, full audit)  basic caching)
```

### Choose Redis Community when:
- Running local development, testing, or staging environments.
- Building standard caching layers where occasional node restarts and manual failovers do not impact business continuity.
- Operating under strict open-source / zero-software-license budget requirements.

### Choose Redis Software when:
- Data residency, HIPAA, PCI-DSS, or financial sovereignty mandates that no data leaves private corporate data centers.
- You operate a private cloud or Kubernetes infrastructure and require predictable, multi-tenant database provisioning for internal teams.
- You need high throughput across multiple shards without introducing cluster-aware complexity into legacy application codebases.

### Choose Redis Cloud when:
- Building modern cloud architectures (AWS/GCP/Azure) and aiming to eliminate database administration overhead.
- Requiring automatic scaling, instant zero-downtime shard rebalancing, and global multi-region Active-Active deployments.

## 6. System Design & Interview Quick Reference

> [!WARNING] Single-Threaded Event Loop Gotcha
> The core execution engine of open-source Redis processes commands sequentially using a single-threaded event loop (I/O multiplexing via `epoll`/`kqueue`).
> - **Dangerous Commands in Production**: `KEYS *`, `FLUSHALL`, `HGETALL` on massive sets. These block the entire server for all clients.
> - **Safe Alternatives**: `SCAN`, `HSCAN`, `SSCAN` (cursor-based iteration with time complexity $O(1)$ per step).

### Key Architectural Concepts for Interviews
1. **Hash Slot Allocation ($16,384$)**:
   - Why not $2^{16} = 65,536$? Gossip heartbeat packets would carry an excessively large bitmap overhead ($8\text{ KB}$ vs $2\text{ KB}$). 16,384 provides an optimal balance between cluster size limit (up to 1,000 nodes) and heartbeat packet efficiency.
2. **Persistence Trade-Offs**:
   - **RDB (Snapshot)**: Point-in-time compact binary file. Fast recovery, but risks data loss between snapshot intervals.
   - **AOF (Append Only File)**: Logs every write command. Higher durability (`fsync=everysec`), larger disk footprint, slower restart replay.
   - **Production Standard**: Hybrid persistence (RDB snapshot + AOF tail replay).
3. **Eviction Policies**:
   - Know the difference between `noeviction` (returns errors on memory limit), `allkeys-lru` / `allkeys-lfu` (ideal for pure caching), and `volatile-lru` (only evicts keys with an explicit TTL set).
